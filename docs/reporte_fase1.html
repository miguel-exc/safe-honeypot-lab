Sección 01

Contexto técnico necesario para esta fase

¿Qué es un honeypot SSH?

Un honeypot es un sistema señuelo diseñado para atraer a atacantes, registrar sus acciones y generar inteligencia de amenazas (CTI). Un honeypot SSH simula un servidor Linux accesible por SSH: acepta credenciales débiles, emula un shell interactivo y registra cada comando ejecutado. Su valor no radica en la respuesta que da al atacante, sino en los datos que recopila.

Los honeypots se clasifican por nivel de interacción: los de baja interacción simulan pocos servicios y responden de forma estática; los de alta interacción exponen un sistema real y capturan TTPs detallados pero son costosos y peligrosos. Los honeypots como Cowrie se ubican en el rango medio-alto: emulan un sistema completo con filesystem falso pero sin ejecutar código real.

Arquitectura de Cowrie

Capa de transporte (SSH)

Implementada con Twisted Conch. Negocia claves, cifrado y autenticación. Expone el puerto 2222 internamente. La versión del banner (SSH-2.0-OpenSSH_8.9p1) es configurable para fingerprinting realista.

Realm y Avatar

El realm decide qué "backend" maneja la sesión autenticada. En Cowrie hay dos: shell (filesystem emulado) y llm (respuestas generadas por LLM). El avatar encapsula identidad del usuario conectado.

Shell emulado (backend shell)

Implementa ~60 comandos Unix: ls, cd, cat, wget, curl, etc. sobre un filesystem virtual. Estado consistente entre comandos. Respuestas deterministas y rápidas.

Output plugins

Eventos JSON estructurados (cowrie.json) y texto plano (cowrie.log). Cada evento tiene eventid, src_ip, sensor, timestamp. Los IDs relevantes son: cowrie.login.success, cowrie.command.input, cowrie.session.closed.

LLM backend en Cowrie (módulo experimental)

Cowrie 3.1.3 incluye un módulo experimental cowrie/llm/ que reemplaza completamente el backend shell por respuestas generadas por un LLM. Cuando backend = llm está configurado, cada comando del atacante se envía como prompt a una API OpenAI-compatible y la respuesta se devuelve al terminal. El módulo incluye:

  • llm.py — cliente HTTP asíncrono (Twisted Agent) para APIs OpenAI/Anthropic
  • protocol.py — protocolos de sesión interactiva (HoneyPotInteractiveProtocol) y exec (HoneyPotExecProtocol)
  • realm.py / avatar.py — realm alternativo al shell
  • session.py — adaptador ISession que instancia los protocolos LLM

Ollama y modelos locales

Ollama es un servidor local que sirve modelos LLM con una API compatible con OpenAI en http://localhost:11434. Permite ejecutar modelos de lenguaje sin enviar datos a la nube, lo que es crítico para los requerimientos de seguridad del proyecto. El modelo llama3.2:3b (Meta, 2024) pesa 2.0 GB y puede ejecutarse en CPU en un Mac con 16 GB RAM con latencia aceptable (~260 ms por respuesta).

Redes Docker y aislamiento

Docker permite crear redes internal: true que bloquean todo tráfico hacia internet (no hay gateway por defecto). Los contenedores en esa red sólo pueden comunicarse entre sí. Para que el honeypot LLM pueda alcanzar Ollama (en el host Mac), se necesita una segunda red no-interna donde host.docker.internal resuelve la IP del host.

Sección 03

Toma de decisiones y justificación de herramientas

Plataforma de virtualización: Docker Desktop en macOS
✓ Elegido

El entorno disponible es un Mac con Apple Silicon y 16 GB RAM. Docker Desktop ofrece aislamiento de red (internal: true), reconstrucción rápida de entornos (docker compose down && up) y no consume la RAM que necesitaría una VM completa para 2–3 nodos.

Alternativas descartadas: VirtualBox / VMware — no soportan Apple Silicon de forma nativa; KVM — requiere Linux host; cloud VMs — violan el requisito de red totalmente aislada y LLM local.
Honeypot base: Cowrie
✓ Elegido

Cowrie es el honeypot SSH de referencia académica (más de 3.5k citas en la literatura). Genera cowrie.json con esquema documentado, soporta TTY logging, captura hashes de archivos descargados, y tiene imagen Docker oficial mantenida. Imagen cowrie/cowrie:latest usa Cowrie 3.1.3 con Python 3.13.

Alternativas descartadas: Kippo — obsoleto, antecesor de Cowrie; HoneySSH — sin mantenimiento activo; implementación propia — semanas insuficientes.
Motor LLM: Ollama con llama3.2:3b
✓ Elegido

Los requerimientos del proyecto exigen LLM 100% local (sin llamadas a APIs cloud), sin capacidad de herramientas/funciones. Ollama expone una API compatible con OpenAI en http://localhost:11434. El modelo llama3.2:3b pesa 2.0 GB, corre en CPU en 16 GB RAM, responde en ~260 ms y no necesita GPU.

Alternativas descartadas: OpenAI GPT-4o — requiere API key y llamadas a internet (violación de requerimiento); Llama 3.1 8B — demasiado lento en CPU sin GPU; Mistral 7B — misma limitación de RAM; modelos cuantizados GGUF directos — Ollama ya los sirve, no hay ventaja en acceder directo.
Backend híbrido: módulo LLM oficial de Cowrie
✓ Elegido

Cowrie 3.1.x incluye un módulo cowrie/llm/ experimental que activa un realm SSH alternativo con backend = llm. Al usar la misma imagen Docker, el mismo cowrie.json, el mismo protocolo SSH y la misma persona de host, se minimizan las variables entre Condición A y B. La comparación experimental es más limpia.

Alternativas descartadas: HoneyLLM — codebase separado, stack SSH diferente, formato de log diferente; HoneyGPT — código no completamente público; implementación propia — semana 45 es demasiado corta para construir desde cero y mantener la validez metodológica.
Persona del host: prod-web-01 (Ubuntu + Apache + MySQL)
✓ Elegido

Una persona de servidor web de producción es la más frecuente en campañas de compromiso masivo. Hostname descriptivo, banner SSH de Ubuntu 22.04 auténtico, credenciales débiles predecibles (root/admin, admin/admin, etc.) para maximizar la tasa de logins simulados en el experimento.

Estrategia de red: dos redes Docker
✓ Elegido

El contenedor safe-honeypot-llm necesita simultáneamente: (a) estar aislado de internet para los atacantes (safe-net, internal: true), y (b) poder alcanzar Ollama en el host Mac (llm-net, bridge normal). La solución con dos redes mantiene el aislamiento sin proxy adicional.

Alternativa descartada: Proxy intermediario — añade un contenedor innecesario y una superficie de ataque extra en la red experimental.
Sección 04

Hallazgos técnicos y correcciones

Durante la implementación del backend LLM se identificaron tres bugs no documentados en el módulo experimental de Cowrie. Las correcciones se aplican vía volume bind-mount de un archivo parche (honeypot/llm_protocol_patch.py) sobre el código original del contenedor.

BUG-01 · protocol.py · HoneyPotExecProtocol
Race condition: EOF de stdin cierra el canal antes de que llegue la respuesta LLM

Causa raíz: Al ejecutar un comando exec (ssh host "id"), el cliente SSH cierra su stdin inmediatamente después de enviar el comando. Esto dispara HoneyPotBaseProtocol.eofReceived(), que llama a processEnded(exitCode=0) en ~3 ms. El canal SSH se cierra. La respuesta LLM llega en ~260 ms, pero self.terminal ya es None y se descarta silenciosamente.

Corrección: Override de eofReceived en HoneyPotExecProtocol para que sólo registre el estado sin cerrar el canal. El cierre correcto lo hace _handle_exec_response tras recibir la respuesta del LLM.

def eofReceived(self) -> None:
    # No llamar processEnded aquí — esperar respuesta LLM
    self._stdin_eof = True
BUG-02 · protocol.py · _process_exec_with_llm
Comandos exec no se registran en cowrie.json

Causa raíz: _process_exec_with_llm construye el prompt y envía la petición LLM pero nunca despacha el evento cowrie.command.input. Los comandos exec no aparecen en cowrie.json, sólo login y cierre de sesión.

Corrección: Añadir dispatch explícito del evento antes de la llamada LLM, replicando el comportamiento de HoneyPotBaseProtocol.lineReceived para sesiones interactivas.

self.events.dispatch(
    "cowrie.command.input",
    "CMD: %(input)s",
    input=self.execcmd
)
BUG-03 · protocol.py + cowrie-llm.cfg
Ollama antepone "assistant\n\n" a las respuestas

Causa raíz: Cuando el cuerpo de la petición OpenAI contiene sólo un mensaje system sin mensaje user, el modelo llama3.2:3b genera la respuesta precedida de su etiqueta de rol (assistant\n\n). El módulo original construye el prompt exec como [system_context] sin mensaje de usuario.

Corrección: (1) Añadir el comando exec como mensaje de usuario en el prompt: prompt = [system_context, self.execcmd]. (2) Añadir limpieza de etiquetas de rol en strip_markdown().

# En strip_markdown():
text = re.sub(r"^(assistant|user|system)\s*\n+",
              "", text, flags=re.IGNORECASE)
