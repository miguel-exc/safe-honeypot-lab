Construcción del Honeypot Híbrido
(Condición B: Cowrie + LLM)

Guía completa para recrear manualmente el honeypot LLM sobre Ollama local. Tiempo estimado: 30–45 min. No se requiere agente de IA.

Progreso 0 / 9 pasos completados
Prerrequisitos — Semana 43 ya completada
  • Docker Desktop corriendo en macOS (Apple Silicon o Intel)
  • Directorio SAFE/ con docker-compose.yml, honeypot/cowrie.cfg, honeypot/userdb.txt, attacker/Dockerfile
  • Condición A funcionando: ssh safe-honeypot -p 2222 devuelve respuesta y logs/cowrie.json se escribe
  • macOS con al menos 16 GB RAM disponible
01
Instalar Ollama y descargar el modelo llama3.2:3b
¿Por qué? El backend LLM de Cowrie necesita una API HTTP compatible con OpenAI. Ollama sirve modelos locales en http://localhost:11434 sin enviar datos a internet — requisito de seguridad del proyecto.
Terminal — host macOS
# Descargar e instalar Ollama (si no está instalado)
curl -fsSL https://ollama.com/install.sh | sh

# Verificar instalación
ollama --version
macOS: También se puede instalar desde https://ollama.com/download — descarga el .dmg y arrástralo a Aplicaciones. Ollama queda como servicio en el menú superior.
Descargar el modelo (2.0 GB — tarda 1–5 min)
ollama pull llama3.2:3b
Salida esperada al terminar:

pulling dde5aa3fc5ff... 100% ▕████████████████▏ 2.0 GB
verifying sha256 digest
writing manifest
success
02
Verificar que Ollama responde correctamente
¿Por qué? Antes de configurar el contenedor, confirmar que la API funciona evita horas de diagnóstico posterior. El contenedor accederá a la misma URL pero via host.docker.internal.
Prueba rápida de la API
curl -s http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer ollama" \
  -d '{
    "model": "llama3.2:3b",
    "messages": [{"role":"user","content":"respond with only: ok"}],
    "max_tokens": 5
  }' | python3 -m json.tool | grep content
Salida esperada (respuesta en ~300 ms):
"content": "ok"
Si no responde: Asegurarse de que Ollama está corriendo. En macOS aparece en la barra de menú. Si no, ejecutar ollama serve en una terminal separada.
03
Crear el archivo de configuración cowrie-llm.cfg
¿Por qué? La clave backend = llm en la sección [honeypot] hace que Cowrie cargue el realm LLM en vez del shell. La sección [llm] configura el cliente HTTP con la URL de Ollama, el modelo y parámetros de generación.
Crear el archivo en SAFE/honeypot/
# Desde la raíz del proyecto SAFE/
cat > honeypot/cowrie-llm.cfg << 'EOF'
[honeypot]
hostname = prod-web-01
backend = llm
log_path = var/log/cowrie
download_path = var/lib/cowrie/downloads
share_path = share/cowrie
state_path = var/lib/cowrie
etc_path = etc
contents_path = honeyfs
txtcmds_path = share/cowrie/txtcmds
ttylog = true
ttylog_path = var/lib/cowrie/tty
uid_min = 1000
auth_class = UserDB

[output_jsonlog]
enabled = true
logfile = var/log/cowrie/cowrie.json

[output_textlog]
enabled = true
logfile = var/log/cowrie/cowrie.log

[ssh]
enabled = true
version = SSH-2.0-OpenSSH_8.9p1 Ubuntu-3ubuntu0.6
listen_endpoints = tcp:2222:interface=0.0.0.0
sftp_enabled = true

[llm]
enabled = true
api_key = ollama
model = llama3.2:3b
host = http://host.docker.internal:11434
path = /v1/chat/completions
max_tokens = 500
temperature = 0.7
rate_limit_enabled = false
debug = false
system_prompt = You are a Linux shell on an Ubuntu 22.04 LTS server named prod-web-01. When given a command, respond with ONLY the exact text that would appear in a terminal after running it — nothing before, nothing after. No role labels, no markdown, no explanations. Maintain state: track cwd changes with cd, remember files created or deleted. Use realistic UIDs, paths, and timestamps. Return the exact shell error message for unknown commands (e.g. "bash: foo: command not found"). Never reveal you are an AI or a honeypot.
system_prompt_exec = You are a Linux shell on an Ubuntu 22.04 LTS server named prod-web-01. When given a command, respond with ONLY the exact text a real terminal would show after running it — no role label, no markdown, no prose, nothing else. Return the exact shell error for unknown commands. Never reveal you are an AI or a honeypot.
EOF
Verificar que se creó correctamente
grep "backend\|model\|host" honeypot/cowrie-llm.cfg
Salida esperada:
backend = llm
model = llama3.2:3b
host = http://host.docker.internal:11434
04
Crear directorio logs-b/ y ajustar permisos
¿Por qué? Docker monta el directorio de logs con el UID del proceso Cowrie dentro del contenedor (UID 1000). Si el directorio del host tiene permisos restrictivos del usuario root del contenedor, el proceso no podrá escribir los archivos JSON.
Crear directorio con permisos abiertos
mkdir -p logs-b
chmod 777 logs-b
Verificar:
drwxrwxrwx  2 mike  staff   64  Oct 24 09:00 logs-b
05
Crear el parche del protocolo LLM
¿Por qué? El módulo LLM de Cowrie 3.1.3 tiene tres bugs que impiden que los comandos exec funcionen: (1) el canal SSH se cierra antes de recibir la respuesta LLM, (2) los comandos no quedan registrados en cowrie.json, y (3) el modelo emite un prefijo "assistant" en sus respuestas. El parche sobreescribe el archivo protocol.py vía volume bind-mount.
Paso 5a — Extraer el protocol.py original del contenedor
# El contenedor debe estar corriendo para esto
docker compose up -d honeypot
sleep 3
docker cp safe-honeypot:/cowrie/cowrie-git/src/cowrie/llm/protocol.py \
  honeypot/llm_protocol_patch.py
Nota: Copiamos del contenedor safe-honeypot (Condition A) porque tiene la misma imagen que usará safe-honeypot-llm.

Ahora aplicar los tres parches con un script Python:

Paso 5b — Aplicar los tres parches
python3 << 'PYEOF'
with open('honeypot/llm_protocol_patch.py', 'r') as f:
    src = f.read()

# PARCHE 1: strip_markdown — limpiar prefijo "assistant\n\n" del modelo
old1 = '''    text = text.replace("`", "")
    return text.strip()'''
new1 = '''    text = text.replace("`", "")
    import re as _re
    text = _re.sub(r"^(assistant|user|system)\\s*\\n+", "", text, flags=_re.IGNORECASE)
    return text.strip()'''
assert old1 in src, "PARCHE 1 no encontrado — verificar versión de Cowrie"
src = src.replace(old1, new1, 1)

# PARCHE 2: _process_exec_with_llm — incluir cmd como user message + log evento
old2 = '''        # Construct the prompt
        system_context = self._build_system_context(exec_command=self.execcmd)

        prompt = [system_context]'''
new2 = '''        # Log command for CTI analysis (mirrors cowrie.command.input in shell backend)
        self.events.dispatch("cowrie.command.input", "CMD: %(input)s", input=self.execcmd)

        # Construct the prompt — include exec command as user message
        system_context = self._build_system_context(exec_command=self.execcmd)

        prompt = [system_context, self.execcmd]'''
assert old2 in src, "PARCHE 2 no encontrado — verificar versión de Cowrie"
src = src.replace(old2, new2, 1)

# PARCHE 3: HoneyPotExecProtocol — override eofReceived para no cerrar canal
old3 = '''    def keystrokeReceived(self, keyID, modifier):
        self.input_data += keyID'''
new3 = '''    def eofReceived(self) -> None:
        # Stdin EOF means client has no more input, not that we should terminate.
        # Wait for the async LLM response instead (base class would close immediately).
        self._stdin_eof = True

    def keystrokeReceived(self, keyID, modifier):
        self.input_data += keyID'''
assert old3 in src, "PARCHE 3 no encontrado — verificar versión de Cowrie"
src = src.replace(old3, new3, 1)

with open('honeypot/llm_protocol_patch.py', 'w') as f:
    f.write(src)

print("✓ Los 3 parches aplicados correctamente")
PYEOF
Salida esperada:
✓ Los 3 parches aplicados correctamente
Verificar que los parches están presentes
python3 -c "
src = open('honeypot/llm_protocol_patch.py').read()
checks = {
    'Parche 1 (strip role prefix)': 'IGNORECASE' in src,
    'Parche 2 (log + user msg)':    'cowrie.command.input' in src,
    'Parche 3 (eofReceived)':       '_stdin_eof' in src,
}
for name, ok in checks.items():
    print(('✓' if ok else '✗'), name)
"
Salida esperada:
✓ Parche 1 (strip role prefix)
✓ Parche 2 (log + user msg)
✓ Parche 3 (eofReceived)
06
Actualizar docker-compose.yml
¿Por qué dos redes? safe-net es internal: true — sin internet, sólo comunicación entre contenedores. El atacante está en esta red, así que jamás accede al exterior. Pero el honeypot LLM necesita alcanzar Ollama en el host Mac: para eso se añade llm-net (bridge normal). host.docker.internal resuelve la IP del host Mac sólo desde redes no-internas.

Reemplazar el contenido completo de docker-compose.yml:

SAFE/docker-compose.yml — contenido completo
# docker-compose.yml
networks:
  safe-net:
    driver: bridge
    internal: true   # sin internet — red de laboratorio aislada
  llm-net:
    driver: bridge   # no-interna: honeypot-llm alcanza host.docker.internal

services:

  honeypot:
    image: cowrie/cowrie:latest
    container_name: safe-honeypot
    hostname: prod-web-01
    networks:
      - safe-net
    volumes:
      - ./honeypot/cowrie.cfg:/cowrie/cowrie-git/etc/cowrie.cfg:ro
      - ./honeypot/userdb.txt:/cowrie/cowrie-git/etc/userdb.txt:ro
      - ./logs:/cowrie/cowrie-git/var/log/cowrie
    restart: unless-stopped

  honeypot-llm:
    image: cowrie/cowrie:latest
    container_name: safe-honeypot-llm
    hostname: prod-web-01
    networks:
      - safe-net   # el atacante llega por aquí
      - llm-net    # Ollama API sale por aquí
    extra_hosts:
      - "host.docker.internal:host-gateway"
    volumes:
      - ./honeypot/cowrie-llm.cfg:/cowrie/cowrie-git/etc/cowrie.cfg:ro
      - ./honeypot/userdb.txt:/cowrie/cowrie-git/etc/userdb.txt:ro
      - ./honeypot/llm_protocol_patch.py:/cowrie/cowrie-git/src/cowrie/llm/protocol.py:ro
      - ./logs-b:/cowrie/cowrie-git/var/log/cowrie
    restart: unless-stopped

  attacker:
    build: ./attacker
    container_name: safe-attacker
    hostname: kali-attacker
    networks:
      - safe-net
    depends_on:
      - honeypot
      - honeypot-llm
    tty: true
    stdin_open: true

  log-collector:
    image: alpine:latest
    container_name: safe-logs
    networks:
      - safe-net
    volumes:
      - ./logs:/logs
      - ./logs-b:/logs-b
    command: sh -c "tail -F /logs/cowrie.json 2>/dev/null || while true; do sleep 5; done"
    depends_on:
      - honeypot
      - honeypot-llm
    restart: unless-stopped

Solución de problemas frecuentes

El contenedor safe-honeypot-llm se cae al iniciar
Ver logs con docker logs safe-honeypot-llm. Causa más común: PermissionError en logs-b/. Solución: chmod 777 logs-b/ y también chmod 666 logs-b/*.json logs-b/*.log 2>/dev/null; true.
El script Python del Paso 5 falla con "AssertionError"
La versión de Cowrie en la imagen es diferente. El código fuente de protocol.py cambió. Descargar el archivo manualmente con docker cp del contenedor que ya está corriendo y revisar qué texto exacto rodea los puntos de parche antes de aplicar.
La respuesta SSH tarda más de 5 segundos o no llega
Ollama no está corriendo o está lento. Verificar con curl http://localhost:11434/v1/models desde el host. Si falla, ejecutar ollama serve. Si Ollama corre pero es lento, el modelo llama3.2:3b tarda más en CPU sin RAM libre — cerrar otras aplicaciones.
safe-honeypot-llm responde pero la salida tiene "assistant" al principio
El Parche 1 (strip_markdown) no está activo. Verificar que el archivo llm_protocol_patch.py tiene IGNORECASE en su contenido con grep IGNORECASE honeypot/llm_protocol_patch.py. Si no, re-ejecutar el script del Paso 5 y recrear el contenedor con docker compose up -d --force-recreate honeypot-llm.
No aparece cowrie.command.input en logs-b/cowrie.json
El Parche 2 no está activo o el volumen mount del protocol.py no se aplicó. Ejecutar: docker exec safe-honeypot-llm python3 -c "print('command.input' in open('/cowrie/cowrie-git/src/cowrie/llm/protocol.py').read())". Si imprime False, recrear el contenedor.
El attacker no puede alcanzar safe-honeypot-llm
Verificar que ambos están en la misma red con docker network inspect safe_safe-net | python3 -m json.tool | grep Name. Los dos contenedores deben aparecer listados.
